# SecureBank Security Test Plan

## 1. Purpose

This document maps security requirements and STRIDE threats to regression
tests, expected behavior, and outstanding validation work.

Automated test evidence demonstrates only the scenarios exercised. It does
not establish that every possible attack path is mitigated.

## 2. Test Environment

- Application: Flask SecureBank demo API
- Test framework: pytest
- Test module: `tests/test_bola.py`
- Required test configuration: `JWT_SECRET`
- Test credentials: generated by the test module; do not use production credentials

Run the suite:

    JWT_SECRET="$(python -c 'import secrets; print(secrets.token_hex(32))')" pytest -v

## 3. Authentication and Authorization

| Requirement / Threat | Test | Expected Result | Validation Scope |
|---|---|---|---|
| SEC-01: Authentication required | `test_missing_token_is_rejected`, `test_admin_endpoint_rejects_missing_token` | HTTP 401 | Tested unauthenticated requests |
| SEC-02 / I-001: Account ownership | `test_user_can_access_own_account`, `test_user_cannot_access_another_users_account` | Own account succeeds; cross-user access returns HTTP 403 | Tested account scenarios |
| SEC-03 / S-001: JWT validation | `test_tampered_token_is_rejected`, `test_expired_token_is_rejected`, `test_token_with_wrong_issuer_is_rejected`, `test_token_with_wrong_audience_is_rejected` | Invalid tokens rejected | Tested JWT rejection scenarios |
| S-001: Authorization-header parsing | `test_empty_bearer_token_is_rejected`, `test_basic_auth_scheme_is_rejected`, `test_malformed_authorization_header_is_rejected` | Unsupported or malformed credentials rejected | Tested header formats |
| Login credential validation | `test_login_returns_access_token`, `test_invalid_login_is_rejected`, `test_login_rejects_missing_password`, `test_login_rejects_null_password`, `test_login_rejects_non_string_password`, `test_login_rejects_non_string_usernames`, `test_login_rejects_non_object_json` | Valid login succeeds; invalid inputs are rejected | Tested login cases |
| Password storage | `test_users_store_password_hashes_not_plaintext_passwords` | Password hashes, not plaintext passwords, are stored in the user configuration | Tested in-memory user configuration |
| E-001: Role authorization | `test_regular_user_cannot_access_admin_endpoint`, `test_admin_role_can_access_admin_endpoint`, `test_admin_endpoint_rejects_missing_token` | Regular user receives HTTP 403; configured admin succeeds; missing token receives HTTP 401 | Example admin endpoint only |

## 4. Tampering and Information Disclosure

| Threat | Test | Expected Result | Remaining Work |
|---|---|---|---|
| T-001: Unsupported account modifications | `test_post_to_get_only_account_endpoint_is_rejected`, `test_account_endpoint_rejects_post_method`, `test_account_endpoint_rejects_put_and_patch_methods` | Unsupported methods return HTTP 405 | No account mutation endpoint exists; future mutation operations require separate authorization and integrity tests |
| I-001: Account data exposure | `test_user_can_access_own_account`, `test_user_cannot_access_another_users_account` | Cross-user account access is denied | Extend coverage to additional objects and response fields |

## 5. Audit Logging

| Requirement / Threat | Test | Expected Result | Remaining Work |
|---|---|---|---|
| SEC-07 / R-001: Successful login audit | `test_successful_login_is_audited_without_credentials` | Successful login is audited without credentials in the tested event details | Review broader sensitive-data exposure |
| R-001: Failed login audit | `test_failed_login_is_audited` | Failed login event is recorded | Review event completeness |
| R-001: Authorization-denial audit | `test_cross_account_access_is_audited`, `test_missing_token_rejection_is_audited` | Tested denials produce audit events | Review broader event coverage |
| R-001: Persistence and integrity | `test_audit_event_persists_and_hash_chain_verifies`, `test_audit_log_tampering_is_detected` | Persisted log verifies; tested tampering is detected | External protection, independent checkpoints, and retention remain unverified |
| R-001: File permissions | `test_audit_log_file_has_restrictive_permissions` | Log file has restrictive permissions in the test environment | Validate deployment-specific filesystem controls |

## 6. Denial of Service

| Requirement / Threat | Test | Expected Result | Remaining Work |
|---|---|---|---|
| SEC-08 / D-001: Login rate limiting | `test_login_rate_limit_returns_429` | Requests exceeding the configured limit receive HTTP 429 | Distributed-client abuse and broader resource-exhaustion testing |
| D-001: Account rate limiting | `test_account_rate_limit_returns_429` | Requests exceeding the configured limit receive HTTP 429 | Multi-worker shared storage and production behavior |
| D-001: Admin endpoint rate limiting | No dedicated rate-limit test identified in the current test inventory | Configured limit is 30 requests per minute per client IP | Add a dedicated regression test |
| D-001: Other resource limits | No evidence identified for request-size limits, timeouts, or resource quotas | Not established by the current test suite | Assess and implement appropriate controls where needed |

## 7. Security Tooling and CI

| Requirement | Validation Method | Scope / Limitation |
|---|---|---|
| SEC-05: Secrets in source control | Gitleaks workflow scan | A clean scan applies to the scanned repository history and tool configuration |
| SEC-06: Dependency and configuration security | Trivy workflow scan | CI configures vulnerability, misconfiguration, and secret scanners; container-image scanning is not established by the current workflow |
| SEC-10: Automated security checks | `.github/workflows/security.yml` | Four jobs are configured: regression tests, Semgrep, Trivy, and Gitleaks; check the latest run for its result |
| SEC-04: Parameterized database queries | Not applicable to the current in-memory account model | Reassess when database queries are introduced; add query-safety tests at that time |

## 8. Signing-Key and Identity Lifecycle

| Requirement / Threat | Current Evidence | Remaining Work |
|---|---|---|
| AUTH-004: Signing-key handling | Application requires `JWT_SECRET` from the environment and fails startup if it is missing | Production secrets management, secure provisioning, rotation, and revocation are unverified |
| AUTH-005: Credential brute force | Login rate limit is configured and its HTTP 429 behavior is tested | Credential stuffing, distributed abuse, and production shared-storage behavior remain unverified |
| Identity lifecycle | Demo users and environment-provided password hashes are used | Persistent identity management and production lifecycle controls are outside the current implementation |

## 9. Execution and Evidence Record

For each test run:

1. Record the date, commit, environment, and command.
2. Record the actual pass/fail result.
3. Link failures to defects or remediation work.
4. Update `threat-model/threat-register.csv`,
   `threat-model/threat-test-traceability.md`, and related requirement statuses.
5. Do not label a control fully mitigated based only on a narrow regression test.
